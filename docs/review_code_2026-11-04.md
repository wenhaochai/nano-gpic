## Findings, most severe first

1. **z enters the conditioning about 3 times larger than the timestep embedding, and 40 times larger than its variation over t (JiT_T2I.py:406, :469).** The comment says "z starts as a small part of the conditioning". That is not true. `code_proj` is one Linear with std 0.02, and ‖z‖ = √64 = 8, so code_proj(z) has std 0.16. The timestep embedding has two layers with std 0.02 (JiT_T2I.py:387-388). Measured at init on d640 (random images, 256 values of t from the training law): t_emb std 0.055-0.062; its variation over t 0.0034; code_proj(z) std 0.15-0.16; its variation over images 0.13 (R = 16), 0.078 (R = 64), 0.056 (R = 256). The channel noise alone gives 0.02 · 8 · √(1 − a²) = 0.125 at R = 16 and 0.059 at R = 64. For comparison, the trained w1053 C0/8 EMA has t_emb std 1.44. Failure: in early training, adaLN reads a conditioning vector that is mostly per-image noise, with a very small t signal. This can slow the learning of the t dependence. The point model has no such cost. So the plan A arms can start behind the baseline, and C0/16 (step 33088) is one of the two points of the decision rule. Nothing measures this: the overfit job uses the same init, and the smoke job only checks that values are finite. Fix (one line, before the training runs): `nn.init.normal_(self.code_proj.weight, std=0.02 / self.code_dim ** 0.5)` (output std about 0.02, the size of t_emb), or zero-init the weight. With the weight at zero, the encoder gets a gradient from the second step on. The adaLN output layers are also zero, so it already gets none on the first step. Then re-run test_code.py. Its check 3 sets adaLN to nonzero values but not code_proj, so it still passes with the std init. With a zero init, also set code_proj in that check.

2. **The overfit pass rule can pass with no information, and it can fail because of noise (overfit_code.sh:11, overfit_code.py:84-87).** "covered" counts training images that are the nearest image of a sample with nn_rms < 0.1. That is 5% of the [-1, 1] range. At N = 256 each image gets about 1000 views in 8000 steps (8000 · 32 / 256). My estimate is that no arm reaches nn_rms < 0.1 there. Then covered is 0 for every arm, and "code ≥ point" passes as 0 ≥ 0. At N = 32 the arms draw only 128 samples from one seed. A real tie can then show as code < point, and by the rule a failure stops plan A. The rule also does not say whether "a code arm" means R = 16 or 64, or both. Fix: (a) set the rule before the run: the test counts only if the point arm has near ≥ 0.2 at N = 32. If not, the result is "no information", not "pass". (b) Add metrics with no threshold: the mean nn_rms, and the number of distinct nearest images among all samples divided by N. (c) Pass if, for each code arm, covered ≥ point covered − 2·SE, with SE = √(c(1 − c)/N). (d) At N = 256, run 24000 steps or remove that arm. At about 25 ms per step on one GPU (my estimate, not measured), that is about 10 min. Add a 500-step linear warm-up. Production has 4000 warm-up steps (lite_ladder.yaml), and the overfit job has none (overfit_code.py:65). N = 1 with 8000 steps is enough to check the plumbing.

3. **The decision rule rests on one pair of seeds, and three rates are tested against it.** docs/distribution_step.md:286 requires a gain of more than 5% at both checkpoints. The seed test (w1053 and w1054, docs/text_cache.md:90-97) gave one pair: +2.15% and −3.48%. Plan A also differs from w1053 in ways the rule must absorb: (a) the init of x_embedder and t_embedder. `self.apply(_basic_init)` (JiT_T2I.py:372) reaches the code Linears before JiT_T2I.py:379-388 draws those weights, so their values differ from w1053. (b) The CUDA RNG stream after step 1: code_encode's randn_like, plus the flow's tau and eta. (c) The sample order inside a worker, because gpic_dataset.py:270 hashes the pid (as in the seed test). All of these are "seed" noise. Failure: with three arms, the chance that at least one arm passes both points by noise alone is larger than for one arm. Fix: write in the doc now that a pass of the best R counts only after a second run of that R, or of the baseline, with another `seed_everything` value. Alternative: raise the bar to 5% for the best of three arms.

4. **The start of z is taken from the image noise (JiT_T2I.py:436-440).** 196608 / 64 = 3072, so `flat[:, ::3072]` gives exactly 64 values. All 64 sit in pixel column 0, because 3072 = 12 · 256 and each channel offset is a multiple of 256. So they lie in the 16 tokens of the left patch column, about 4 of 768 values per token. In training, x_T is independent of z. At sampling, these 64 entries are a fixed function of z. I expect no effect on FD. But the docstring's "1/3000" argument is a heuristic, and any effect would be at the left edge. Fix (cheap, optional): draw z0 from its own generator seeded by the prompt's seed. GPICJsonlDataset puts `seed` in the metadata (gpic_jsonl_dataset.py:57, :66), so this keeps one z per prompt on any rank.

5. **The smoke job always exits 0 and checks only finiteness (smoke_code.sh:27-43).** The Python check prints PASS or FAIL to phases.log. The script's status is that of its last `log`. jobs/smoke_implicit.sh does the same, and the user read its log. Fix (optional): make the check exit 1 on FAIL. Also check that the last z_var lies in [1 − a², 1] and that the eval wrote metrics.json.

6. **Small text errors.** docs/distribution_step.md:265, :268 and :283 say +0.5% FLOPs, a flow of about 8 MFLOP and about 66464 steps. The code gives 0.97%, 19 MFLOP and 66176 steps, and the jobs use these correct values. training_code.py:5-6 says the global clip "keeps acting on the main loss alone". That holds only if 0.01 · ‖∇prior‖ ≪ ‖∇fm‖, and nothing logs it. Fix: correct the doc. Log the prior's gradient norm once per check (training_code.py:57), or drop the sentence.

7. **The overfit arms share the CPUs at compile time (overfit_code.sh:27).** CUDA_VISIBLE_DEVICES gives each arm one GPU, and `dev="cuda"` takes it. OMP_NUM_THREADS=4 limits the intra-op threads. Inductor's compile workers do not follow OMP: up to 32 per process, so 8 · 32 on 96 CPUs. The compile is slower but the results do not change. The 1800 s timeout leaves room. Fix (optional): `TORCHINDUCTOR_COMPILE_THREADS=8`.
