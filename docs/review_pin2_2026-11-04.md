VERDICT: NO-GO, because the per-interval idle count in cpu_wait.py is wrong and the queue fields cannot tell a slow pin thread from slow workers. Both fixes are small.

Review of commit 9f8d137 (branch ladder), 2026-11-04. Tests ran on vis2 at nice 19 with CUDA_VISIBLE_DEVICES empty. Test scripts: /scratch/gpfs/GROUP/USER/tmp/review_pin2/.

## Findings, most severe first

### F1 (high). cpu_wait.py: the idle count at 0.2 s intervals is wrong
- tools/prof/cpu_wait.py:22 reads rq_cpu_time (p[7]) and run_delay (p[8]). The field positions are right for version 17 (see "Checked").
- The kernel adds to rq_cpu_time only when a task leaves the CPU (sched_info_depart). It adds to run_delay only when a waiting task gets a CPU (sched_info_arrive). A task that runs for 0.8 s without a switch adds nothing for 0.8 s, then adds 0.8 s at once.
- Test (tmp/review_pin2/sched_test.py): one busy loop alone on cpu95 of vis2. Over 0.2 s intervals, rq_cpu_time gave a busy share of 0.00, 0.00, 3.81, 0.93, 1.20, 1.00, 0.64, 1.06, 1.71, 0.46. /proc/stat gave an idle share of 0.00 in every interval.
- A data worker makes one batch per about 0.9 s (32 workers per rank, 27 ms per step) and computes most of that time. So cpu_wait.py:74 counts many busy CPUs as idle. Line 76 ("share of intervals with >=4 idle CPUs and >=2 of wait") then reports "waiting while CPUs are idle" in every arm, the control included. On vis2, with two busy stand-in workers per rank, the tool printed share 1.000 on both sockets.
- Failure: the one output that tests the hypothesis directly gives a false positive in every arm.
- Still valid: the per-CPU busy% and wait% over the whole 30 s window (line 78) and the per-rank worker sums (lines 79-87). Their error is at most one run span per CPU.
- Fix: per interval, read the idle and iowait ticks of each CPU from /proc/stat. That test showed 0.00 idle for the busy CPU and 0.70-0.90 for an idle CPU, at 20 ticks per interval. For the wait, read field 3 (state) and field 39 (last CPU) of /proc/<pid>/stat for the 256 worker pids in each interval. That is about 1300 file reads per second. Count the workers in state R on each socket. When that count is higher than the busy CPUs of the socket and the socket has 4 or more idle CPUs, a worker is waiting while CPUs are idle. As a coarser check, also record procs_running from /proc/stat: it gives running plus waiting tasks for the whole node at that moment.

### F2 (high). The queue fields cannot tell a slow pin thread from slow workers. q_out repeats q_ahead
- baselines/PixelGen/src/callbacks/bench.py:121. In torch 2.7.1 (envs/pixgen), q_ahead + q_out is constant. After next() returns, _process_data calls _try_put_index (torch/utils/data/dataloader.py:1546-1548), which refills to prefetch_factor x workers. In production that is 4 x 32 = 128. So q_out = 128 - q_ahead and adds no information.
- Test (tmp/review_pin2/q_test.py; 8 workers, prefetch 4, one worker delayed 0.5 s for 2 batches):
  - steady state: q_ready 31, q_ahead 0, q_out 32
  - after the late worker: q_ready 0, q_ahead 28, q_out 4
  So q_ahead does identify one late worker.
- q_ready counts only pinned batches in _data_queue (dataloader.py:1179-1196). Batches that workers finished but the pin thread did not yet copy sit in _worker_result_queue and are not counted. So "q_ready 0, q_ahead 0" occurs both when the workers as a whole fell behind and when the pin thread is waiting for a CPU.
- The second case is likely. In w1048, the pt_data_pin thread of rank 3 waited for a CPU 32.6% of the wall clock in the pin arm, against 10.1% in the w1055 control (tmp/ladder_prof/host_prof/ladder_kern_1103_1945/d640_pin/thread_wait.txt and ladder_host3_1104_0357/d640_control/thread_wait.txt).
- Fix: replace q_out with q_raw=it._worker_result_queue.qsize(). On Linux this is a semaphore read, and the test printed it without error. q_raw > 0 with q_ready = 0 means a late pin thread.

### F3 (medium). The kernel hypothesis is weak as written, and the job does not isolate it
From upstream CFS (kernel/sched/fair.c, 5.x; not checked against the RHEL 5.14.0-687 source, see "Not checked"):
1. load_balance does not stop at an all-pinned queue. When can_migrate_task refuses every task of the busiest queue, LBF_ALL_PINNED stays set. load_balance then clears that CPU from its mask and goes back to `redo` while other CPUs remain. It goes to out_all_pinned only when no candidate CPU is left. So one queue with two pinned threads cannot block a balance pass by itself.
2. When the balancing CPU is newly idle (newidle_balance), out_one_pinned skips the doubling of balance_interval ("newidle_balance() disregards balance intervals"). The doubling and MAX_PINNED_INTERVAL (512 ms) apply only to the periodic balance. That balance changes per CPU and per domain, so a back-off on one CPU does not stop other CPUs. An idle CPU still pulls through newidle balance and nohz idle balance, and a waking worker is placed on an idle CPU of the LLC by select_idle_sibling.
3. "A queue with one running thread is not a pull candidate" is only partly true. find_busiest_queue skips a queue with one task only for migrate_load when its load exceeds the imbalance. detach_tasks needs nr_running > 1, but the active-balance path can pick a queue with one task. When that task cannot run on this_cpu, the path goes to out_one_pinned, which also doubles the interval.
4. Main and autograd alternate, so their shared queue mostly holds one runnable thread, not two.
So the mechanism can still occur, but upstream code gives it no strong support. The docstring at host_tuning.py:42-44 and the job header (jobs/smoke_ladder_pin2.sh:11-12) state it as the likely cause.

What each cause predicts in the outputs of this job:

| cause | pin2 vs pin1 stalls | q fields at a stall (with F2's q_raw) | cpu_wait (with F1's fix) | thread_wait, rank 3 |
|---|---|---|---|---|
| A. balance back-off (hypothesis) | gone | ready 0, ahead small, raw 0 | pin1: workers R > busy CPUs while >=4 idle; pin2: no | worker wait falls toward 2.7 |
| B. nice-0 daemon preempts a pinned thread | the same | stall step: main thread's own run delay jumps; queue fields normal | none | main wait low on average, spikes not visible over 15 s |
| C. the pin thread waits for a CPU | the same or worse (40 against 44 worker CPUs) | ready 0, ahead 0, raw > 0 | socket near full | pt_data_pin wait about 30% |
| D. worker CPU capacity | worse in pin2 | ready falls over the steps before; ahead 0, raw 0 | few idle CPUs, high wait | worker wait high |
| E. cache or wake-up cost of two CPUs | no change; median of pin2 higher than pin1 by tenths of a ms | normal | none | none |

- B cannot be separated with the job as it is. The stall step shows only a long data_wait_s, and that wait includes any time the main thread did not run.
- Cheap addition: in bench.py:117-121, also record the run_delay (second field) of /proc/thread-self/schedstat for the main thread, and of /proc/self/task/<it._pin_memory_thread.native_id>/schedstat for the pin thread, in each row. That is two small file reads per step, tens of microseconds. A jump in the main thread's run delay at the stall step marks B. A jump in the pin thread's run delay marks C.
- An observation that points to a per-worker cause. In w1048 d640_pin (tmp/ladder_prof/pin_stalls.py, threshold 200 ms), there are 24 long steps. Step 0 is the first step. Two of the long steps (after steps 999 and 1999, 3.7 and 2.6 s, all ranks) are the last.ckpt saves (last_every = 1000). Without these 3, 21 remain. Of the 20 gaps between the 21 remaining long steps, 14 lie within 3 steps of a multiple of 32. By chance that rate is about 22%. Each rank has 32 workers that deliver in turn, so a worker slot comes back every 32 steps. That fits "one late worker", and q_ahead tests it directly.

### F4 (medium). bench.py:117-121 has no guard
- In this setup it does not raise:
  - _iterator is None before the first iter(); line 120 skips it.
  - Lightning's fetcher calls iter() before the first on_train_batch_start (fit_loop.py:276, fetchers.py:104-117).
  - DataLoader caches _iterator only when persistent_workers is set and num_workers > 0 (gpic_dataset.py:415-416). So it is always a _MultiProcessingDataLoaderIter, which has all three attributes (test: "same object: True").
  - With GPIC_PROF_CYCLE_BATCHES the shut-down iterator still has the attributes.
  - A resume builds the same loader.
  - _reset replaces _task_info with a new dict, and only the main thread changes it, so reading it on the main thread is safe.
- But any later change (num_workers 0 with a cached iterator, a torch upgrade that renames _task_info) would raise AttributeError in a callback and kill the run.
- Fix: wrap lines 119-121 in try/except Exception, as host_tuning.py:135-140 does.

### F5 (low). Both measurement windows contain the step-1000 checkpoint save
- jobs/smoke_ladder_pin2.sh:42-44. The windows start 20 s after "[warmup] done" and last 15 s and 30 s. At about 29.5 ms per step, they cover steps of about 680-1190 and 680-1700.
- train_ladder.sh:27 sets last_every = 32000/32 = 1000, so the save at step 1000 (3.7 s in w1048) falls in both windows. During the save, the workers fill their queues and CPUs go idle. That shifts the idle and wait means by about 12% of the cpu_wait window, by a different amount in each arm.
- Fix: sleep 40 s and measure for 25 s. That covers steps of about 1350-2200 and ends about 7 s before an arm at 2400 steps ends. Or exclude the save interval when analyzing.

### F6 (low). The arm limits can exceed --time
- Lines 49-61 allow 4 x 300 + 2 x 420 = 2040 s, plus up to 60 s of timeout -k per arm. That totals 40 min, against --time=00:35:00 (line 5).
- The typical run is about 21 min (w1055 had the same arm lengths: 03:57:53 to 04:18:37). A hung arm that runs to its limit would let the host cut the d1280 pair.
- Fix: --time=00:42:00, or a limit of 270 s for the d640 arms (w1055's arms took 182-197 s).

### F7 (low). The adoption rule needs exact wording
Line 13. The 3% threshold is about 0.9 ms. That is about 9 times the within-job spread of the two controls in w1055 (29.5 and 29.4 ms), and about 2 times the spread across jobs (29.4-29.8 ms in w1048, w1051 and w1055). So the threshold is sound for the d640 mean. Fix the wording before the run:
- (a) Measure steps 100-2400 without the save steps, as tmp/ladder_prof/arm_table.py does.
- (b) "No more steps over 0.3 s than the controls" means no more than the larger count of the two controls. In w1055 both counts were 0, so a single long step blocks adoption. That is strict and acceptable.
- (c) d1280 has one control. Across jobs its mean varied by 0.4 ms (88.1-88.5 ms), about 0.5%. So the 0.5% bound sits at the noise level: a pass or a fail there is weak evidence.
- (d) Adoption is a speed decision. A pass does not confirm the kernel mechanism (F3).

### F8 (low). The monitors in wait_arm can run on the reserved CPUs
- Lines 43-44 start thread_wait.py and cpu_wait.py from the batch shell, which may use all 96 CPUs. A snapshot of about 3600 threads by thread_wait.py takes CPU for a short time. At equal nice 19 it can delay a pinned main thread, and only in the pin arms.
- Fix: run both under `taskset -c` with the CPUs outside the reserved set (0-79 for PIN=2, 0-87 for PIN=1).

### F9 (low). The [numa] line changed for PIN=1
- host_tuning.py:77 now prints "main thread on CPU c, autograd thread on CPU c" in place of "main and autograd threads on CPU c".
- No script parses this line (searched tools/, jobs/, tmp/ladder_prof/). docs/review_kernels_2026-11-03.md:59-60 and :190 tell a reader to grep the old text. A grep for it will find 0 lines in this job.

### F10 (info). PIN=2 also removes worker CPUs
- PIN=2 leaves 40 CPUs per socket for 128 workers and the other threads. PIN=1 leaves 44 and the control 48 (host_tuning.py:48-51).
- The workers used 58-58.5 CPUs on the node in w1048 and w1055, about 29 per socket, so 40 is enough on average. If PIN=2 is slower, cause D and the hypothesis are confounded. Read the per-CPU busy% of cpu_wait (line 78) before drawing a conclusion.

## Checked and found correct
- Production with both variables unset:
  - HostTuning._pin is False (host_tuning.py:103) and _pin_split is not used.
  - BenchTimer.queue_on is False (bench.py:66). BenchTimer is loaded only when BENCH_OUT is set (train_ladder.sh:35-36), and train_ladder.sh does not set BENCH_OUT.
  - No production code path changes.
- The math is unchanged when the variables are set. The changes set CPU affinity and read loader attributes. Nothing changes a tensor, the RNG or the data order.
- PIN=1 against 89dbf49 (git diff 89dbf49 9f8d137): with split=False, reserved = socket[-4:], core = reserved[index % 4], autograd_core = core. The worker and other-thread moves are the same lines.
  - The differences: the log text, the guard (16 against 8 CPUs), and the new idle_workers/seed code, which is gated by its own variables.
  - Each socket has 48 CPUs (node-k16g2: Sockets=2, CoresPerSocket=48, ThreadsPerCore=1), so the guard passes.
- PIN=2 layout:
  - node0 (even CPUs): main threads on 80, 82, 84, 86 and autograd threads on 88, 90, 92, 94 for GPUs 0-3.
  - node1: 81-87 and 89-95 for GPUs 4-7.
  - The GPU-to-node map is 0-3 on node 0 and 4-7 on node 1 (w1055 log). index % 4 therefore gives distinct CPUs within each socket.
- Env:
  - GPIC_PROF_QUEUE is exported (line 24) and reaches all ranks.
  - A `VAR=x function` prefix reaches the arm and does not stay for the next arm. w1055 used the same form: d640_idle had [idle] lines and d640_control2 had none.
- wait_arm:
  - `grep "END $1 "` has a trailing space, so d640_control does not match d640_control2.
  - It returns when the arm ends before the warm-up.
  - The inner `wait` waits only for its own two monitors.
  - Each arm has a fresh LADDER_RUN_ROOT, so no arm resumes.
  - timeout signals its whole process group, so no ranks are left over.
- pgrep -u <uid> -f 'main.py fit': the job takes all 8 GPUs, so the pilot cannot run another GPU guest beside it. Only own-user processes match. No process of the job's shells contains "main.py fit". The scripts read /proc only and change no job state.
- cpu_wait.py:
  - Version 17 cpu line: cpuN yld_count, 0, sched_count, sched_goidle, ttwu_count, ttwu_local, rq_cpu_time, run_delay, pcount. So p[7] and p[8] are rq_cpu_time and run_delay.
  - These two fields are filled with kernel.sched_schedstats = 0 (login1 shows nonzero values while the first six are 0).
  - The import works under python3 -I: line 12 adds the script's directory to sys.path. It ran under -I on vis2.
- The worker-to-rank mapping (cpu_wait.py:43-57, the same logic as thread_wait.py:73-82):
  - Rank 0's main has no LOCAL_RANK in /proc/<pid>/environ and a parent outside the set.
  - Rank k's main has LOCAL_RANK=k and parent rank 0, whose value is None.
  - A worker has its main's value, because a fork copies the original environ block.
  - Confirmed: w1048 thread_wait gave "264 processes, 8 ranks". The stand-in test on vis2 gave 2.0 CPUs for each rank's two busy workers.
  - In that test, the ssh command line also matched "main.py fit" and counted as a third rank. In the job, no other process has that command line.
- bench.py timing: Lightning prefetches one batch. When on_train_batch_start runs, the loader has already returned the next batch (fetchers.py:121-129, training_epoch_loop.py:311-334). So the q fields and data_wait_s describe the same fetch. That is consistent.
- Cost per step: one qsize (a mutex), one pass over a dict of at most 128 entries, one integer read. A few microseconds against 27 ms.

## Not checked

- The sched domain layout of the GPU nodes (SNC mode, LLC size). /proc/sys/kernel/sched_domain does not exist, and the schedstat domain lines are 0.

- Any GPU run of this commit.

## Fixes (2026-11-04)

- F1: cpu_wait.py reads the idle ticks of /proc/stat per interval and each worker's state and last CPU, and counts idle CPUs only among those the workers may use. It also prints the workers with the largest wait.
- F2: q_out is replaced by q_raw (the workers' result queue). q_rcvd is added, which names the worker that delivered each batch.
- F3: the docstring and job header no longer state the balance back-off as the likely cause. Each row records the run delay of the main thread and of the pin thread.
- F4: the queue code is in try/except, and it stops with one log line.
- F5: the monitors start 40 s after the warm-up. thread_wait runs 15 s, cpu_wait 25 s.
- F6: --time is 42 min.
- F7: the adoption rule in the job header has the exact wording.
- F8: the monitors run under taskset -c 0-79.
- F9: the [numa] line keeps its old text for PIN=1.
- F10: read at analysis.
